# Модель авторизации

> Frontend-проверки в этом репозитории нужны **только для UX**: они прячут недоступные разделы и объясняют отказ. Защитой данных они не являются. Любой пользователь может изменить код в браузере или вызвать API напрямую, поэтому каждое решение о доступе обязан принимать backend.

## 1. Роли и области видимости

| Роль | Код | Scope | Назначение |
|---|---|---|---|
| Руководитель системы образования | `education_head` | `system` | Сводная картина по округам и школам, прогнозы, сведения о модели |
| Аналитик | `analyst` | `system` | То же плюс технические страницы: метрики модели, мониторинг, распределения признаков |
| Директор школы | `school_director` | `school(school_id)` | Только своя школа; `school_id` обязателен |

## 2. Права (permissions)

| Permission | head | analyst | director | Описание |
|---|:-:|:-:|:-:|---|
| `system:view` | ✓ | ✓ | — | Агрегаты по системе и округам, district breakdown |
| `schools:list` | ✓ | ✓ | — | Список всех школ |
| `school:view` | ✓ | ✓ | своя | Карточка школы |
| `teachers:view` | ✓ | ✓ | своя | Реестр и профили педагогов |
| `analytics:view` | ✓ | ✓ | своя | Аналитика в пределах scope |
| `forecast:use` | ✓ | ✓ | своя | Калькулятор; reference-школа только в scope |
| `model:view_summary` | ✓ | ✓ | ✓ | Версия и статус модели, глобальная значимость |
| `model:view_technical` | — | ✓ | — | Метрики, confusion matrix, калибровка |
| `model:monitoring` | — | ✓ | — | Журнал инференса, дрейф |
| `data:catalog` | ✓ | ✓ | — | Источники, качество данных |
| `model:retrain` | — | — | — | Только admin/ML-инженер через CLI или защищённый endpoint |

Реализация во frontend: `src/auth/access.ts` (`ROLE_PERMISSIONS`, `scopeOf`, `can`, `canViewSchool`).

## 3. Enforcement

### Frontend (UX)
- Навигация строится по правам (`navItems`). Директор видит «Моя школа» вместо «Школы».
- Фильтр округа для директора скрыт и заменён закреплённой плашкой школы. Параметр `district` из URL игнорируется.
- `#/schools` для директора перенаправляет на `#/schools/<own>`.
- `#/schools/<other>` показывает «Недостаточно прав для просмотра этой школы» и кнопку «Перейти к моей школе».
- Хлебные крошки директора не ведут на глобальный список.
- Страницы без права показывают ForbiddenState.

### Mock-backend (имитация сервера)
`MockContext` создаётся для конкретного пользователя, и каждая выборка проходит через `schoolIds()` и `canViewSchool()`:
- `schools.list` возвращает только свою школу, фильтр округа scope не расширяет;
- `schools.getProfile(other)` → 403, в том числе для несуществующего id (проверка scope идёт **до** проверки существования, чтобы нельзя было перебирать id);
- `teachers.getProfile` → 403, если у педагога нет срезов в школах scope. Школы вне scope в траектории обезличены («Другая школа»);
- `dashboard.getDistrictBreakdown` → 403 для директора;
- `forecast.predict` с `school.mode=reference` на чужую школу → 403.

Всё это покрыто тестами `src/data/mock/directorScope.test.ts`.

### Backend (production, обязательно)
1. **Аутентификация**: OIDC (корпоративный IdP), короткоживущий JWT; роль и `school_id` берутся из `auth.user_role`, а не из запроса.
2. **RBAC-зависимость FastAPI**: `require(permission)` на каждом роутере.
3. **School-scoped queries**: репозитории принимают `Scope` и всегда добавляют `WHERE school_id = :scope_school_id`. SQL без scope-параметра запрещён (lint-правило и code review).
4. **Запрет IDOR**: ресурсы по id (`/schools/{id}`, `/teachers/{id}`) сначала проверяются на принадлежность scope. Для директора ответ на чужой или несуществующий id одинаковый (403), без различий во времени ответа.
5. **Row-Level Security** в PostgreSQL как второй рубеж: `SET app.school_scope = …` на соединение, политики на `core.teacher_year`, `core.mobility_outcome`, `marts.*`.
6. **Агрегаты**: директору недоступны эндпоинты уровня системы и округа. Иначе он мог бы вычесть данные своей школы и получить чужие.
7. **Малые группы**: доли по группам с n < 5 подавляются (`MIN_GROUP_SIZE`) на сервере — и для директора, и для системных ролей.
8. **Аудит**: журнал обращений к профилям педагогов (кто, когда, какой id), хранение 1 год.
9. **Rate limiting** на `/forecast` и реестр.

## 4. Приватность и минимизация данных

- В системе есть только обезличенный `teacher_id`. ФИО, СНИЛС и контакты не загружаются. Если ID источника связан с персоной, ETL заменяет его на HMAC-псевдоним.
- Реестр отдаёт только поля, нужные для анализа. Пол показывается в профиле, но не используется для фильтрации и сортировки в реестре.
- Точные даты (присвоения категории, документов ПК) видны в профиле, а в ML используются как «лет с…».
- Журнал инференса не хранит входные признаки и ID педагога. Сохраняются версия модели, вероятности, класс, latency и `request_id`.
- Правовые основания: обработка обезличенных данных для статистики и исследований, локальные акты ОО, согласия на обработку (лонгрид, раздел 3).

## 5. Использование прогнозов

Прогноз служит поддержкой решения и не является основанием для кадровых мер. Интерфейс не показывает «рейтинг риска» педагогов списком. Прогноз по конкретному профилю доступен только в калькуляторе, с дисклеймером. См. ML_ARCHITECTURE.md §12.
