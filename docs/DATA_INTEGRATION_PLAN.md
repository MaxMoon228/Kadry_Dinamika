# План интеграции реального датасета

Источник истины по составу данных — Приложение 1 «Описание данных» (выборка ДОНМ, 2022–2024). Эталонная реализация правил ниже находится в `src/data/adapters/normalize.ts` и покрыта тестами `normalize.test.ts`. Backend-ETL на Python должен повторять её один в один.

## 1. Ожидаемые таблицы

| Таблица | Гранулярность строки | Ключ источника |
|---|---|---|
| Учителя | педагог × год × предмет × параллель | (Идентификатор, Год, Предмет, Параллель) — **не уникален** при совместительстве |
| Образование | запись об образовании × год (накопительно) | нет, дедупликация по всем полям |
| Повышение квалификации | программа × педагог | нет, дедупликация по всем полям |
| Школы | школа × год | (Школа, Год) |

**Открытые вопросы (проверить на первой выгрузке):**
1. Как задан год среза: колонка, файл или лист? В коде предполагается колонка `Год`.
2. Стабилен ли `Идентификатор` между годами и школами? Без этого target построить нельзя.
3. Совпадают ли названия школ в таблицах «Учителя» и «Школы» (формат, кавычки, реорганизации)?
4. Дата среза: на какую дату сформирована выгрузка (сентябрь / декабрь / май)?
5. Бывает ли у педагога несколько школ в одном году (совместительство) и как отмечена основная?
6. Значения «Квалификационная категория», в том числе новые (педагог-методист, педагог-наставник по приказу № 196).
7. Покрывает ли выгрузка все школы города или только выборку? Это влияет на интерпретацию класса 2.
8. Таблица «Школы» дана по каждому году или единым снимком?

## 2. Ключи и связи

```
school (school_id PK, natural_key UNIQUE, name, district)
school_year (school_id FK, year, building_count, student_count)          PK(school_id, year)
teacher (teacher_id PK)                                                  -- только обезличенный ID
teacher_year (teacher_id FK, year, school_id FK, …скаляры)               PK(teacher_id, year)
teacher_assignment (teacher_id, year, subject, parallel)                 PK(all)
teacher_education (edu_id PK, teacher_id FK, type, institution, graduation_date, specialization, qualification, first_seen_year)
teacher_training (training_id PK, teacher_id FK, program_name, program_type, provider, hours, document_date)
mobility_outcome (teacher_id, from_year, to_year, status, from_school_id, to_school_id)  PK(teacher_id, from_year)
```

- `school_id`: суррогатный ключ от нормализованного названия (`schoolIdFromName`: lower-case, без кавычек, схлопнутые пробелы, FNV-1a). В production нужна таблица соответствий `school_alias(natural_key → school_id)` для переименований.
- `teacher.teacher_id` = `Идентификатор` источника. Если ID содержит персональные данные, его нужно псевдонимизировать (HMAC с секретом на стороне ETL).

## 3. Временная структура

- Срез = год `t` ∈ {2022, 2023, 2024}.
- Период мобильности = `t → t+1`: **наблюдается только 2022→2023 и 2023→2024**.
- Срез 2024 — это когорта для прогноза 2024→2025 (inference), для обучения он без target.
- В UI «мобильность за год Y» означает период `Y−1 → Y`. Для 2022 года показывается пояснение, а не пустые нули.

## 4. Типы, nullable и нормализация полей

Полная таблица полей — в `DATA_DICTIONARY.md`. Общие правила:

| Правило | Реализация |
|---|---|
| Пробелы | trim + схлопывание повторов |
| Пустые значения | `""`, `—`, `-`, `nan`, `null` → NULL |
| Числа | запятая → точка; нечисловое → NULL + счётчик в отчёте |
| Даты | `YYYY-MM-DD`, `DD.MM.YYYY`, `YYYY` → ISO; иначе NULL |
| Пол | `Ж/Женский/F` → female, `М/Мужской/M` → male |
| Да/Нет | → boolean, иначе NULL |
| Категория | `Высш*` → Высшая, `Перв*` → Первая, `Втор*` → Вторая, `Без*`/пусто → NULL; прочие значения сохраняются и попадают в отчёт |
| Предпроф. класс | пусто / «Нет» → NULL (не преподаёт), иначе направление |
| Тип ПК/ПП | только `ПК` / `ПП`, иначе строка отбрасывается с отметкой в отчёте |

Категориальные признаки: основная должность, направление деятельности, предмет, параллель, учёная степень, категория, предпроф. направление, тип образования, специализация, квалификация, учебное заведение, тип программы, организатор, округ, школа.

## 5. Дедупликация

1. Точные дубли строк в каждой таблице удаляются (`exactDuplicatesRemoved`).
2. «Учителя»: строки группируются по `(teacher_id, year)`, и из них строится один `teacher_year`. Скалярные поля берутся по моде непустых значений; если значения расходятся, срез считается в `conflictingTeacherYears` и уходит на ручную проверку.
3. «Образование»: записи, одинаковые по всем полям, кроме года, схлопываются в одну с `first_seen_year = min(Год)` (`cumulativeEducationCollapsed`).
4. «ПК/ПП»: дедупликация по (ID, программа, тип, организатор, часы, дата).

## 6. Несколько предметов, образований, программ

- **Предметы и параллели**: хранятся как множество `assignments`. Признаки для ML: `subject_count`, `parallel_count`, основной предмет (первый по частоте строк) и multi-hot по топ-N предметов. В аналитике педагог учитывается в каждом своём предмете (суммы по предметам > числа педагогов, это указано в подписи графика).
- **Образование**: для ML агрегаты — `has_higher_education`, `education_record_count`, `years_since_graduation` (последнее окончание ≤ среза), тип и специализация основного (высшего) образования.
- **ПК/ПП**: агрегаты на дату среза — `training_count`, `training_hours_total`, `training_hours_recent_3y`, `has_professional_retraining`, `years_since_last_training`.

## 7. Совместительство (несколько школ в году)

Основная школа — та, у которой больше строк «предмет × параллель». При равенстве выбирается лексикографически первый `school_id`. Такие случаи считаются в `multiSchoolTeacherYears`. Если в данных есть признак основного места работы, использовать его. Смена основной школы при сохранении второй — пограничный случай для класса 1; решение фиксируется с экспертом.

## 8. Построение teacher-year snapshot и target

```
for t in years where t+1 in years:
  for s in teacher_year[t]:
    n = teacher_year[t+1].get(s.teacher_id)
    status = 2 if n is None else (0 if n.school_id == s.school_id else 1)
```

Ограничения интерпретации класса 2: отсутствие в выгрузке t+1 включает пенсию, декрет, длительный отпуск, переход в школы вне охвата выборки или в другой регион, а также ошибки выгрузки. Это нужно фиксировать в выводах. По возможности проверить «возвраты»: педагог отсутствует в t+1 и появляется в t+2 (для 2022 это наблюдаемо).

## 9. Data validation (на каждую загрузку)

| Проверка | Порог / действие |
|---|---|
| Схема: все колонки Приложения 1 присутствуют | иначе загрузка отклоняется |
| Уникальность `(teacher_id, year)` после нормализации | 100% |
| Доля строк со школой вне справочника | < 1%, иначе стоп |
| `0 ≤ пед. стаж ≤ общий стаж ≤ возраст − 14` | нарушения → отчёт, значения → NULL |
| Возраст 18–80 | иначе NULL |
| Даты ≤ дата среза (категория, документы ПК) | иначе NULL + отчёт |
| Пропуски по ключевым полям | отчёт, сравнение с прошлой загрузкой |
| Новые значения категориальных полей | отчёт (unseen categories) |
| Резкое изменение численности школы год к году (> 40%) | ручная проверка |

Инструменты: pandera или great_expectations в ETL; отчёт сохраняется вместе с `dataset_version`.

## 10. Риски утечки данных (leakage)

1. **Признаки из t+1**: все признаки строго из среза `t`. Документы ПК и даты категорий — только с датой ≤ даты среза (`deriveTeacherFeatures`, валидация калькулятора).
2. **Школьные агрегаты по target** (например, «доля ушедших в школе»): считаются только по прошлым периодам (`t−1 → t`), не включая текущий. Для первого периода признак отсутствует.
3. **Target encoding** категорий — только внутри обучающих фолдов (out-of-fold) и только по train-периоду.
4. **Численность педагогов школы в t+1** напрямую отражает уходы. Используется только численность в t.
5. **Один педагог в train и validation**: при временном split педагог 2022 г. и он же в 2023 г. попадают в разные наборы. Это допустимо, потому что признаки меняются, но для CV внутри периода нужна `GroupKFold` по `teacher_id`.
6. **Нормализация и скейлинг** обучаются только на train.

## 11. Train/inference consistency

- Единый пакет `ml.features` строит признаки и из `core.teacher_year`, и из `ForecastInput` (обе ветки через одну функцию `build_features(teacher_snapshot, education, training, school_year)`). Во frontend аналог — `snapshotToForecastInput`.
- `feature_schema_version` хранится в артефакте модели и проверяется при inference.
- Школьные признаки при `school.mode = reference` берутся сервером из `school_year` того же года — ровно так, как при обучении.
- Справочники категорий фиксируются при обучении, неизвестные значения на inference кодируются как `__unknown__` и логируются.

## 12. Шаги подключения

1. Положить выгрузки в защищённое хранилище (не в git).
2. Реализовать `etl/load_raw.py` → `raw.*` (без преобразований, с `load_id`).
3. Реализовать `etl/normalize.py` по правилам выше и прогнать тестовые кейсы из `normalize.test.ts`, портированные на pytest.
4. Сверить отчёт качества с ожиданиями и ответить на открытые вопросы из раздела 1.
5. Построить `marts.*` и эндпоинты из `API_CONTRACT.md`.
6. Во frontend: `VITE_DATA_SOURCE=api`, `VITE_API_BASE_URL=…`. Изменения в страницах не требуются.

## Локальный режим с реальными данными

Промежуточный шаг до backend: реальные данные показываются без сервера БД — локально и на GitHub Pages. **Реализовано.**

```
D:/CU/KAdri/*.xlsx ──► scripts/real-data/build_real_dataset.py ──► public/data/real-dataset.json (в репозитории)
                         (пайплайн ноутбука «Неделя 4»)                       │
                                             vite dev / GitHub Pages: <BASE_URL>data/real-dataset.json
                                                                              │
                     bootstrapDataSource() → decodeRealDataset() → DatasetIndex → in-memory репозитории (scope, DTO)
```

- Формат `kd-real-dataset@1`: колоночные массивы и словарь строк (~15 МБ, сжато ~3 МБ). Схема описана в `RealDatasetFile` (`src/data/local/realDataset.ts`).
- Сверка с ноутбуком (`realDataset.test.ts`): 52 723 строк «педагог × год», 34 790 известных исходов, 266 школ, 561 исправленная опечатка, доля ушедших 12,9%.
- Ограничения: данные целиком загружаются в браузер, поэтому scope директора здесь реализован так же, как в mock, и это **не** мера безопасности. Для разграничения доступа нужен backend (раздел 12).
