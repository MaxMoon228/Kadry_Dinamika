# ML-архитектура: прогноз трудовой мобильности педагогов

Статус: **проект**. Модель не обучена; на синтетических данных обучение не проводится и проводиться не должно.

## 1. Постановка

- Объект: педагог в срезе года `t` (teacher-year snapshot).
- Target `y ∈ {0, 1, 2}` для периода `t → t+1`: 0 — остался в своей школе, 1 — перешёл в другую школу, 2 — ушёл из системы образования.
- Задача: **многоклассовая классификация** с калиброванными вероятностями `P(y=k | x_t)`.
- Связь с курсом: в лонгриде основная задача описана как бинарная («уход с должности»), а целевая переменная в Приложении 1 задана тремя классами. Принимаем 3-классовую постановку как основную. Бинарные проекции (2 vs {0,1}; {1,2} vs 0) считаем вспомогательными: для сравнения с литературой и для метрик Recall/F2 по классу «ушёл».
- Использование: поддержка решений (decision support), а не автоматическое решение.

## 2. Данные и временная структура

| Период | Признаки | Target | Роль |
|---|---|---|---|
| P1 | срез 2022 | присутствие в 2023 | train |
| P2 | срез 2023 | присутствие в 2024 | validation/test (out-of-time) |
| P3 | срез 2024 | — (2025 не наблюдается) | inference-когорта |

Главный принцип: **признаки известны до события**. Всё, что относится к `t+1`, недоступно (DATA_INTEGRATION_PLAN §10).

## 3. Признаки

Оценки: доступность (A: всегда есть / B: частые пропуски), бизнес-смысл, leakage risk, bias risk, encoding.

| `gender` | A | Слабый, вероятно косвенный | нет | **высокий** | бинарный; по умолчанию **исключён** из модели, используется только для fairness-аудита |

| `activity_direction` | A | Предметная область | нет | низкий | CatBoost native / target enc (OOF) |
| `subjects` (основной) | A | Дефицитные предметы | нет | низкий | CatBoost native |
| `academic_degree` | A (редкий) | Уровень квалификации | нет | низкий | one-hot |

### 3.2 Derived

| Признак | Формула | Leakage-контроль |
|---|---|---|
| `students_per_teacher` | student_count / teacher_count (t) | только t |
| `teacher_count` | уникальные педагоги школы (t) | только t |
| `subject_count`, `parallel_count` | по assignments | — |
| `experience_gap` | total − pedagogical | — |
| `years_since_qualification` | t − год присвоения | — |
| `qualification_remaining_years` | год окончания − t | если срок задан |
| `training_count`, `training_hours_total`, `training_hours_recent_3y` | документы с датой ≤ 31.12.t | дата ≤ среза |
| `has_professional_retraining` | ∃ ПП ≤ среза | дата ≤ среза |
| `years_since_last_training` | t − год последнего документа | NULL → «нет» + флаг |
| `years_since_graduation`, `has_higher_education` | по образованию с `first_seen_year ≤ t` | — |
| `school_under35_share`, `school_with_category_share` | агрегаты школы (t) | только t |
| `school_mobility_prev_{move,leave}` | доли исходов школы за (t−1 → t) | **только прошлый период**; для P1 недоступно → признак можно ввести только при появлении 2021 или при обучении на P2 |
| `years_observed_in_school` | число подряд идущих срезов в школе | цензурировано слева, учитывать с осторожностью |

Не включаем автоматически все признаки: отбор ведётся по результатам EDA, стабильности важности между P1 и P2 и fairness-аудиту (§11).

### 3.3 Пропуски и выбросы
- Числовые: медиана по train + флаг `is_missing_*` (для линейных моделей); для деревьев — нативная обработка (CatBoost/LightGBM) или та же медиана.
- Категориальные: отдельная категория `__missing__` (лонгрид: «отсутствие значения само по себе информативно»).
- Выбросы: IQR / z-score только для диагностики. Невозможные значения (стаж > возраста) обнуляются в ETL, правдоподобные крайние значения сохраняются.

## 4. Валидация

1. **Основная (out-of-time)**: train = P1, test = P2. Это единственная честная оценка обобщения во времени.
2. **Внутри train (подбор гиперпараметров)**: `StratifiedGroupKFold(k=5, group=teacher_id, stratify=y)` по P1. Такой вариант отвечает рекомендации курса о стратифицированной CV и исключает утечку через одного педагога.
3. **Финальная модель**: переобучается на P1 ∪ P2 с зафиксированными гиперпараметрами для inference на P3. Метрики берутся с шага 1.
4. **Устойчивость**: bootstrap-интервалы (1000 ресэмплов) для Macro F1 и Recall(2) на P2; сравнение важности признаков P1 и P2.

Random split по всем строкам **запрещён**: он смешивает периоды и одного педагога.

## 5. Модели

| # | Модель | Зачем |
|---|---|---|
| 0 | `DummyClassifier(strategy="prior")` и `"stratified"` | нижняя граница |
| 1 | Multinomial Logistic Regression (L2; L1/elastic-net через `saga`) + one-hot + scaler | интерпретируемый baseline (курс: Lasso) |
| 2 | Random Forest (`class_weight="balanced_subsample"`) | устойчивость, нелинейность |
| 3 | Gradient Boosting: HistGradientBoosting / LightGBM / XGBoost | сильный табличный baseline (курс: XGBoost) |
| 4 | **CatBoost** (`MultiClass`, `cat_features` нативно, `auto_class_weights="Balanced"` как вариант) | много категориальных признаков, ordered target statistics без утечки |

Критерий выбора: качество (Macro F1, Recall/F2 класса 2, log loss) → устойчивость (разброс по bootstrap и разница CV↔OOT) → калибровка (ECE, Brier) → объяснимость → latency и простота деплоя. Более сложная модель выигрывает только при статистически значимом улучшении (сравнение по bootstrap-интервалам или тест Макнемара по парам).

## 6. Дисбаланс классов

- Отчёт о распределении классов по P1/P2, округам, возрастным группам.
- `class_weight` / `auto_class_weights` — основной инструмент.
- SMOTE и другой oversampling — только при явной пользе и **только внутри обучающих фолдов** (`imblearn.pipeline.Pipeline`), никогда до split.
- Оптимизация идёт не по Accuracy, а по Macro F1 и Recall/F2 класса 2 при контроле log loss.
- Пороги: по умолчанию argmax калиброванных вероятностей. Если нужен повышенный Recall класса 2, подбирается правило «если P(2) ≥ τ, то 2» на CV-фолдах train. Правило документируется и отображается в UI как политика решения, вероятности при этом не меняются.

## 7. Метрики

Для каждого кандидата на P2 и в CV:
- Accuracy, **Balanced Accuracy**, **Macro F1**, Weighted F1;
- Precision / Recall / F1 / **F2** по каждому классу;
- Confusion matrix (абсолютная и нормированная по строкам);
- ROC-AUC OvR (macro), PR-AUC по каждому классу (важнее ROC для редких классов);
- Log loss, Brier score (multiclass), ECE / MCE.

**Бизнес-анализ confusion matrix:**

| Ошибка | Смысл | Цена |
|---|---|---|
| факт 2 → прогноз 0 | пропущен уход из системы | высокая: упущена возможность удержания |
| факт 0 → прогноз 2 | ложная тревога | средняя: лишнее внимание, риск стигматизации |
| факт 1 ↔ 2 | путаница «перешёл» / «ушёл» | для системы разная цена: переход сохраняет педагога в системе |
| факт 1 → прогноз 0 | пропущен переход | для школы важно, для системы менее критично |

Дополнительно считается cost-weighted score с матрицей стоимостей, согласованной с заказчиком. Как основной критерий он не используется.

## 8. Калибровка

- Диагностика: reliability diagram по каждому классу (OvR), ECE, Brier на P2.
- Методы: temperature scaling (для логитов бустинга; один параметр, устойчив на малых данных), isotonic / sigmoid через `CalibratedClassifierCV(cv=…)` на отложенных фолдах train; для multiclass — нормировка после OvR-калибровки.
- Калибратор обучается на данных, не участвовавших в обучении модели (CV внутри train или отдельный hold-out P1). P2 используется только для проверки.
- Если после калибровки ECE > 0.05 на P2, UI показывает вероятности бинами («низкая / средняя / высокая») или с явным предупреждением. `calibrated=false` уже отображается в калькуляторе.

## 9. Explainability

**Глобальная:** permutation importance (P2), mean |SHAP| по классам, SHAP summary / beeswarm, PDP/ICE для числовых признаков (возраст, стаж, часы ПК), коэффициенты логистической регрессии для сравнения.

**Локальная (калькулятор):** TreeExplainer для деревьев или LinearExplainer для baseline. На каждый класс возвращаются top-k вкладов. Вклады переводятся из log-odds в вероятности (разность вероятностей с последовательным добавлением признаков или `shap` с `model_output="probability"` через interventional background из train).

Контракт `ForecastExplanation.contributions[].impact` задаёт вклад в вероятность каждого класса. Сумма вкладов ≈ `probabilities − baseProbabilities` (mock уже соблюдает это инвариант через точные значения Шепли).

Формулировки в UI: «повлиял на прогноз модели», «связан с увеличением / уменьшением прогнозной вероятности». Формулировки «причина увольнения» и «из-за» запрещены.

**Анализ ошибок:** подгруппы с систематическим завышением или занижением P(2) (slice analysis по округу, предмету, возрасту и стажу), типичные и атипичные случаи (Приложение 2, этап 10).

## 10. Жизненный цикл, реестр и дообучение

```
new data → validation (DATA_INTEGRATION_PLAN §9) → normalize → features (ml.features, schema vN)
 → temporal split → training (кандидаты §5) → evaluation (§7) → calibration (§8)
 → explainability checks (стабильность топ-признаков, отсутствие leakage-подозрений:
   AUC > 0.95 или один признак > 50% важности = стоп)
 → fairness audit (§11) → artifact (model + calibrator + pipeline + schema + card)
 → MLflow registry: stage=Staging (challenger)
 → сравнение с champion на одном и том же OOT-наборе
 → ручное approval (ML-инженер + владелец продукта), model card
 → promote → Production; старый champion → Archived (rollback за 1 команду)
```

Новая модель **не** заменяет production автоматически. Правило промоушена: Macro F1 и Recall(2) не хуже champion (с учётом доверительных интервалов), ECE ≤ champion + 0.01, fairness-гэпы не растут.

Метаданные артефакта (MLflow tags/params): `model_version`, `training_timestamp`, `dataset_version` (хеш raw-выгрузок + версия ETL), `feature_schema_version`, `git_commit`, `hyperparameters`, `train_periods`, `test_period`, метрики, калибратор, `class_distribution`, ссылка на fairness-отчёт.

Реестр: **MLflow** (tracking + model registry) с artifact store в S3-совместимом хранилище (MinIO) и backend store в PostgreSQL. Минимальный вариант на старте: filesystem artifacts + таблица `ml.model_registry_ref`. Frontend от MLflow не зависит.

Retraining: ежегодно после появления нового среза (естественный ритм данных) или досрочно по триггерам §11. Запускается командой `python -m ml.training.train --config …` или admin-эндпоинтом `POST /admin/model/retrain` (асинхронная задача). UI этой операции не выполняет.

## 11. Мониторинг, дрейф, fairness

**Журнал инференса** (`ml.inference_log`): `request_id`, `timestamp`, `model_version`, `input_schema_version`, вероятности, predicted class, latency, `school_id` (для scope-аналитики), `actual_outcome` (заполняется после среза t+1 для пакетного скоринга когорты). Входные признаки и ID педагога **не хранятся**. Для анализа дрейфа сохраняются агрегированные гистограммы признаков по дням.

**Дрейф и деградация:**
- Data drift: PSI (> 0.2 — сигнал) по числовым признакам, χ²/JS по категориальным; доля unseen categories (> 2%); доля пропусков (рост > 5 п.п.).
- Prediction drift: распределение predicted class и средней уверенности.
- Label drift: распределение классов в новом срезе в сравнении с train.
- Performance: после наблюдения t+1 пересчитываются Macro F1, Recall(2), log loss на когорте.
- Calibration drift: ECE на новой когорте.

Триггеры переобучения: новый годовой срез; PSI > 0.25 по одному из топ-5 признаков; падение Macro F1 > 0.05 или Recall(2) > 0.1; ECE > 0.08; изменение справочников (новые категории по приказу № 196).

Страница «Мониторинг модели» (аналитик) уже есть в прототипе: число запросов, распределение прогнозов, уверенность, latency, последние запросы. Панели drift, calibration и actual-vs-predicted запланированы.

**Fairness-аудит** (если юридически и методологически допустимо): по группам пола, возрастных групп и округов сравниваются Recall, FPR и FNR класса 2, calibration-in-the-large, средняя P(2). Порог разрыва — ≤ 0.1 по Recall или FNR, иначе нужен разбор: исключение признака, reweighting, раздельная калибровка. Пол по умолчанию не входит в модель. Возраст входит, так как объясняет выход на пенсию, но требует аудита и осторожных формулировок.

## 12. Этика и интерпретация

- Прогноз не является фактом будущего поведения. Это вероятность, оценённая по историческим паттернам 2022–2024 гг.
- Прогноз **нельзя** использовать как основание для увольнения, наказания, отказа в найме или давления. Метрики «не должны быть инструментом давления» (лонгрид).
- Human-in-the-loop: решения принимает руководитель с учётом контекста. Система помогает найти группы, требующие внимания (наставничество, поддержка молодых специалистов, нагрузка), а не отдельных «виноватых».
- В UI нет списков «педагогов с высоким риском». Агрегированный прогноз показывается по группам (с подавлением малых групп), индивидуальный — только в калькуляторе по введённому профилю и с дисклеймером.
- Класс 2 включает естественные причины (пенсия, декрет). Высокая P(2) у педагога 63 лет не означает проблему школы.
- Ограничения: 2 обучающих периода, цензурированная история, нет причин ухода и условий труда (зарплата, нагрузка). Модель описывает связи, а не причины.
